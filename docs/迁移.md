# 服务器迁移手册

把 DevBrain 整套生产环境从一台 VPS（下称「旧机」）迁移到另一台 VPS（下称「新机」），并在确认无误后下线旧机。本手册按实际执行顺序记录每一步「做什么 + 为什么」，可作为同类迁移的通用模板。

## 适用场景

- 更换云服务器（升配 / 降配 / 换机房 / 换服务商）。
- 整套 Docker Compose 部署的搬迁，且业务数据集中在 Postgres、对象存储在外部（R2）。

## 占位符约定

文档中的命令请按下表替换为实际值（避免在版本库里写死敏感信息）：

| 占位符            | 含义                                       |
| ----------------- | ------------------------------------------ |
| `<旧机>`          | 旧服务器 SSH 目标，如 `root@<旧服务器IP>`  |
| `<新机>`          | 新服务器 SSH 目标，如 `root@<新服务器IP>`  |
| `<新服务器IP>`    | 新服务器公网 IP                            |
| `<域名>`          | 生产域名，对应 `.env` 的 `DEVBRAIN_DOMAIN` |
| `<commit-sha>`    | 旧机当前运行的镜像版本（`IMAGE_TAG` 锚点） |
| `<部署目录>`      | 服务器上的项目目录，如 `/opt/devbrain`     |

> 命令里出现的 `docker compose ...` 默认带上双文件参数：
> `docker compose -f docker-compose.yml -f docker-compose.prod.yml`

## 迁移总览：先想清楚「什么才是命脉」

迁移前最关键的判断是 **哪些数据是真正不可再生的命脉**，这决定了迁移范围：

- 文档原文存在 **Cloudflare R2（外部对象存储）** → 不需要随服务器迁移。
- 服务器本地唯一命脉是 **Postgres 数据卷**（业务数据 + 向量 + 全文索引），体积很小。
- Redis 是 BullMQ 的临时队列状态 → 可丢弃，新机重建即可。
- Caddy 的 TLS 证书卷 → 搬过去可无缝续用，省去重新签发。
- 应用本身（镜像 + 仓库 + `.env`）全部可复现 → 不算「数据」。

> 结论：这是一次「轻数据 + 可复现应用」的迁移，主要工作是**搬一个很小的 Postgres 卷**，其余都是把环境在新机上原样重建。

另一个关键前提：**两台机器跑完全相同的镜像版本（同一个 `<commit-sha>`）**，因此可以放心用「物理卷复制」迁移 Postgres，不必担心版本差异。

## 阶段 0：调研（只读，不改动任何东西）

先摸清两台机器的真实状态，再动手。

1. 确认 SSH 通路：旧机、新机分别能连上。
2. 旧机画像：

   ```bash
   ssh <旧机> 'docker --version; docker compose version; df -h /; \
     cd <部署目录>; docker compose ps; docker volume ls; git rev-parse HEAD'
   ```

3. 新机画像（常见是裸系统）：

   ```bash
   ssh <新机> 'cat /etc/os-release; df -h /; (docker --version || echo "未装 Docker")'
   ```

4. 读取关键配置：`.env` 的键、`docker-compose*.yml`、`infra/caddy/Caddyfile.prod`、DNS 解析、内存占用。

**本阶段要回答的问题：**

- 命脉数据是哪个卷？体积多大？（决定迁移方式与停机时长）
- 新旧镜像版本是否一致？（决定能否物理复制）
- DNS 托管在哪、是否经过 CDN 代理、TTL 多少？（决定切流量方式与生效速度）
- 新机资源是否够跑整套服务？

## 阶段 A：预备新服务器（零停机，旧机照常服务）

这一整个阶段不影响线上，可以从容操作。

1. 新机安装 Docker Engine + compose 插件（按官方 apt 源安装），`systemctl enable --now docker`。
2. 克隆仓库并切到与旧机**完全相同**的版本：

   ```bash
   ssh <新机> 'mkdir -p <部署目录> && git clone <仓库地址> <部署目录> && \
     cd <部署目录> && git checkout <commit-sha>'
   ```

3. 传输 `.env`（**不进版本库的密钥配置**）。用管道直接从旧机流到新机，全程在内存中转、不落地到本地磁盘，并顺手修正与旧机 IP 绑定的值：

   ```bash
   ssh <旧机> 'cat <部署目录>/.env' \
     | sed -E 's#^CORS_ORIGIN=.*#CORS_ORIGIN=https://<域名>#' \
     | ssh <新机> 'cat > <部署目录>/.env && chmod 600 <部署目录>/.env'
   ```

   传完核对行数一致、权限 600、关键键（`IMAGE_TAG`、`DEVBRAIN_DOMAIN`）正确、无旧 IP 残留。

4. 预拉镜像（提前拉好，缩短后面维护窗口）：

   ```bash
   ssh <新机> 'cd <部署目录> && docker compose pull postgres api web worker && \
     docker compose pull caddy redis'
   ```

   > 只拉**实际在线运行**的服务，不要一次性 `pull` 全部（见踩坑①）。

## 阶段 B：维护窗口（短暂停机，迁移数据）

从这里开始线上短暂中断，操作要紧凑。

1. **先做安全网**：导出 Postgres 逻辑备份，存到旧机和本地两份；并记录每张关键表的精确行数作为迁移后的核对基准。

   ```bash
   ssh <旧机> 'docker exec <postgres容器> pg_dump -U <db用户> -d <库名> -Fc \
     -f /tmp/premigrate.dump && docker cp <postgres容器>:/tmp/premigrate.dump \
     <部署目录>/premigrate.dump'
   scp <旧机>:<部署目录>/premigrate.dump ~/migration-backup/
   ```

   行数基准（用精确 `count(*)`，不要用近似的 `n_live_tup`）：

   ```bash
   ssh <旧机> "docker exec -i <postgres容器> psql -U <db用户> -d <库名> -tA <<'SQL'
   select 'User '||count(*) from \"User\";
   select 'Document '||count(*) from \"Document\";
   select 'Chunk '||count(*) from \"Chunk\";
   -- ……其余关键表
   SQL"
   ```

   > psql 里的双引号容易被 SSH/shell 吞掉，用 `<<'SQL'` heredoc 喂语句最稳（见踩坑③）。

2. 停掉旧机整套服务——**务必不带 `-v`**，容器停掉但数据卷全部保留，这是回滚底牌：

   ```bash
   ssh <旧机> 'cd <部署目录> && docker compose down'   # 不要加 -v
   ```

3. 把数据卷从旧机复制到新机。用临时 `alpine` 容器打包/解包，经本地中转（无需在两台服务器之间互配免密）：

   ```bash
   copy_volume() {
     local vol="$1"
     ssh <新机> "docker volume create $vol >/dev/null"
     ssh <旧机> "docker run --rm -v $vol:/from:ro alpine tar -C /from -cf - ." \
       | ssh <新机> "docker run --rm -i -v $vol:/to alpine tar -C /to -xf -"
   }
   copy_volume <pgdata卷>       # 命脉，必须
   copy_volume <caddydata卷>    # TLS 证书，搬过去可无缝续用
   copy_volume <storagedata卷>  # 体积极小，顺手带上
   copy_volume <redisdata卷>    # 可选；临时队列，丢了也能重建
   ```

4. 新机**先只起数据层**，健康后立即核对数据，确认无损再继续：

   ```bash
   ssh <新机> 'cd <部署目录> && docker compose up -d postgres redis'
   ```

   核对扩展版本（如 vector、zhparser）、所有关键表行数、向量字段是否齐全，**必须与阶段 B-1 的基准完全一致**。

5. 跑一次数据库迁移，预期是 no-op（`No pending migrations`），证明 schema 与数据对得上：

   ```bash
   ssh <新机> 'cd <部署目录> && docker compose run --rm -T migrate </dev/null'
   ```

6. 再起应用层：

   ```bash
   ssh <新机> 'cd <部署目录> && docker compose up -d api web worker caddy'
   ```

7. 在新机本地做端到端验证（此时 DNS 还没切，用 `--resolve` 强制指向新机 IP，绕过 DNS）：

   ```bash
   # 健康检查：database 与 redis 都应 ok
   ssh <新机> 'curl -fsS http://127.0.0.1:<api端口>/readyz'
   # 经 Caddy 走真实域名 SNI，验证证书 + 路由 + 重定向
   ssh <新机> 'curl -sS -k -o /dev/null -w "%{http_code}\n" \
     --resolve <域名>:443:127.0.0.1 https://<域名>/login'
   # 检查 Caddy 实际加载的证书有效期
   ssh <新机> 'echo | openssl s_client -connect 127.0.0.1:443 \
     -servername <域名> 2>/dev/null | openssl x509 -noout -subject -issuer -dates'
   ```

   全部通过，说明新机在自己 IP 上已完整可用。

## 阶段 C：切流量

新机验证通过后，再把入口流量切过去。

### 方式一：本机临时验证（只影响自己这台电脑）

在正式切 DNS 前，可以先用本机 `/etc/hosts` 把域名指到新机 IP，单独验证：

```
<新服务器IP> <域名>
<新服务器IP> www.<域名>
```

> macOS 改 hosts 需要 sudo，且必须在真实终端里执行（会提示输密码）。
> 验证完务必把这两行删掉，否则会一直绕过真实 DNS（见踩坑②）。

### 方式二：正式切 DNS（所有人生效）

在 DNS 服务商把 `@` 和 `www` 的 A 记录从旧机 IP 改到 `<新服务器IP>`：

- 若使用 CDN 代理，确认代理开关与原来一致（本项目为 DNS-only，TLS 由 Caddy 直接处理）。
- 低 TTL（如几分钟）会让切换很快生效。
- 证书：若已搬运 caddydata 卷，新机切流量后即刻就有有效证书；后续续期在 DNS 指向新机后自动完成。

切完用真实解析验证证书链被信任（不加 `-k`，看 `ssl_verify_result=0`）：

```bash
curl -sS -o /dev/null -w "%{http_code} verify=%{ssl_verify_result}\n" https://<域名>/login
```

## 阶段 D：收尾（确认无误后再做）

观察一两天、确认线上稳定后：

1. 删除本机 `/etc/hosts` 里的临时覆盖行（如果用过方式一）。
2. 下线旧机（在云控制台关机 / 删除）。**这是不可逆操作，放到最后做。**
3. 更新本地 `~/.ssh/config` 里指向旧机的别名到新机 IP。
4. 按团队备份惯例，对新机做一次 restore-test，确认备份链路正常。

## 踩坑记录

### 踩坑①：`docker compose pull` 因某个未发布镜像整体失败

**问题**：执行 `docker compose pull`（不指定服务）时，某个服务镜像在镜像仓库返回 `denied`，导致整批拉取中断，其它镜像也没拉成。

**原因**：compose 文件里定义了一个**实际并未部署、镜像也从未发布**的服务（如本项目的 `backup`）。compose 的 batch pull 只要有一个失败就整体报错。

**解决**：参照部署脚本，只拉**真正在线运行的服务**：`docker compose pull postgres api web worker`（公共镜像 `caddy`、`redis` 单独拉或在 `up` 时自动拉）。先用 `ssh <旧机> 'docker compose ps'` 确认旧机实际跑了哪些服务，以它为准。

### 踩坑②：本机 `/etc/hosts` 残留覆盖，导致访问的是已停服的旧机

**问题**：迁移后浏览器打不开域名页面，但新机各项检查都正常。

**原因**：本机 `/etc/hosts` 里有一条早先为测试加的覆盖，把域名强制指到**旧机 IP**；而旧机的服务此时已被 `docker compose down` 停掉，443 无响应。浏览器绕过了真实 DNS，自然连不上。

**解决**：检查并修正 `/etc/hosts`：

```bash
grep -i <域名关键字> /etc/hosts          # 排查是否有残留覆盖
# 临时验证：改成新机 IP；验证完删除该行回归真实 DNS
```

**教训**：「检查都正常却访问异常」时，优先怀疑访问链路本身（hosts、DNS 缓存、代理），而不是服务端。注意 `curl` 的 `%{remote_ip}` 在本机存在 DNS/HTTP 代理时可能显示误导值，用 `dscacheutil -q host -a name <域名>`（macOS）看系统真实解析更可靠。

### 踩坑③：psql 语句里的双引号被 shell 吞掉

**问题**：通过 `ssh ... docker exec ... psql -c "select ... \"Table\" ..."` 执行带大小写表名的查询时，双引号被 SSH/shell 多层解析吃掉，Postgres 报「column does not exist」。

**解决**：改用 heredoc 把 SQL 整段喂给 psql，避免层层转义：

```bash
ssh <主机> "docker exec -i <postgres容器> psql -U <db用户> -d <库名> -tA <<'SQL'
select count(*) from \"Chunk\";
SQL"
```

## 通用原则（值得记住）

- **先调研，再动手**：弄清「哪些是真命脉数据」，往往能大幅缩小迁移范围。
- **多重安全网**：逻辑备份（pg_dump）+ 物理卷复制 + 旧机不删，三层兜底。
- **先验证后切流量**：新机在自己 IP 上完整跑通、数据逐表核对一致，才碰流量入口。
- **切流量与销毁资源分开、留缓冲期**：旧机停而不删，作为可随时回滚的快照。
- **不可逆操作放到最后并格外小心**：`compose down` 坚持不带 `-v`；删除服务器留到确认无误后。
